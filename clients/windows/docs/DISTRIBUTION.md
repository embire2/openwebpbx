# Windows Phone distribution and updates

Windows Phone **1.0.0** is a separate client product. It is not the Windows PBX server, Debian package or Android application. The two routes below have implemented build/update paths and separate acceptance requirements. No client release, production update feed, release signature or Store approval has been established.

| Route | Intended target | Installation identity | Updates |
|---|---|---|---|
| Microsoft Store MSIX | Supported Windows 11 x64 | Partner Center-issued name/publisher; currently unknown | Store-delivered MSIX updates |
| Direct MSIX with bundled runtimes | Windows Server 2025 **Desktop Experience**, and separately tested Windows 11 x64 | Independently signed direct-client MSIX/MSIX bundle; final publisher identity and certificate pending | Implemented independent signed **Windows Phone** channel and external updater; native qualification pending |

This choice follows [Microsoft's distribution guidance](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/choose-distribution-path). It does not promise that Microsoft Store is available on Server, or that a desktop UI works on Server Core. Microsoft's current [Windows App SDK support matrix](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/support) does not explicitly list Server 2025; retain that gap and qualify the exact direct build on the intended Server 2025 Desktop Experience installation before claiming support.

## Store flavor

Associate the package with the reserved product before the final build. Development `Name`/`Publisher` values are placeholders, not Store identity. Bundle the native calling libraries and required dependencies; validate the complete MSIX dependency graph and actual install/launch in a clean Windows 11 user session. The upstream SDK offers a separate `windows-store-sdk` source preset; the generic `win64` ZIP alone does not establish Store compatibility. Final native imports and certification-kit results must decide whether that SDK flavor is usable.

Store MSIX obtains Store-managed updates. Do not download and replace its installed program files, launch the direct updater, change Store package identity to force a version, or reuse any PBX-server/Android feed. Open the actual Store listing when user action is needed. Microsoft documents the different update responsibilities in [publish/update guidance](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/publish-first-app). Enterprise and user policies can disable automatic delivery; the client must not promise installation at an exact time or override Windows policy. See [MSIX group policy](https://learn.microsoft.com/en-us/windows/msix/group-policy-msix).

A tenant-required minimum may produce a clear, server-compatible upgrade notice and reject a *new* sign-in when necessary; it is not authority to kill an active call or bypass Store delivery. Preserve an ongoing call and explain recovery if the installed client becomes incompatible. The source implements visible optional/required notices, new-outgoing-call restrictions and repeated idle checks before installation; actual ongoing-call and Store-delivery acceptance remain separate tests.

## Direct flavor

The direct release uses MSIX/MSIX bundles with self-contained .NET and Windows App SDK runtimes plus the pinned native calling libraries. An unpackaged developer build can launch for development, but intentionally refuses automatic update installation because it has no Windows package identity. Final publisher identity, trusted package signing and real package deployment remain release gates.

The implemented direct updater performs these steps:

1. Resolves the actual installed package identity and the same per-user Windows `LocalState` directory used by the packaged app. Store builds use their separate Store path.
2. Verifies the dedicated Windows-phone catalogue with its built-in public key, purpose, product/channel, signature, publication/expiry, sequence/digest floor, package identity/publisher and exact asset length/hash.
3. Downloads the complete bundle into protected per-user staging, verifies it, and shows optional/required update status. Installation checks idle calling state again before and after the user's confirmation and helper readiness.
4. Stages an inventory-checked self-contained updater outside the installed package, using the staging directory as its working directory. The helper verifies the genuine parent's package identity, PID/start time and executable, the original signed envelope, package bytes and saved update floor.
5. The app closes itself only after the helper acknowledges readiness. The helper waits for that process to exit, asks Windows PackageManager to perform the transactional installation, and activates the installed phone again. It never force-kills the user's app or rewrites installed program files itself.

## Installation, privacy and migration checks

Both flavors require a valid tenant address, extension and admin-issued app password, or a bounded one-use invitation. Setup files contain enrolment information, not reusable SIP passwords. Store/normal-user DPAPI profile migration, separate package identities, uninstall, reinstall and changing Windows users must be tested before promising migration between routes. Do not copy another user's protected profile database.

The isolated PostgreSQL admission/policy tests do not establish installed HTTPS onboarding. The next installed acceptance must exercise Windows QR/manual sign-in, password changes, profile policy, tenant isolation and the shared Android device quota through the actual IIS API, then use the issued `owm-` account for native registration and real client media. A synthetic SIP profile in an isolated media lab does not qualify that onboarding path.

Microphone/audio output are required for voice; video additionally needs a supported camera. Device permission denial must leave a clear usable state. Windows11minimum build22000 is a source-declared floor only; final measured memory/disk/CPU requirements remain pending. ARM64, x86, Windows10, Server Core, physical headsets/webcams, RDP media redirection, background incoming delivery and both distribution upgrade paths remain unqualified unless an exact client-specific receipt proves them.

Publish the exact binary, corresponding-source bundle, build instructions, licences/notices, SHA256SUMS, release notes and clear platform limits together. Keep Store and direct client release labels separate from PBXServer20 and mandatory Android18.
