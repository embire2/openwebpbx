# Windows native dependency inventory

`tools/Test-ClientNativeImports.ps1` is a read-only hosted-Windows inventory of an already-published development-package client payload. It requires the exact clean source commit, the existing `phone-package-{nonce}/app` app/updater tree under `RUNNER_TEMP`, an explicit ordinary Microsoft-signed Visual Studio `dumpbin.exe`, and a fresh `phone-native-imports-{32 lowercase hex}.json` report directly under `RUNNER_TEMP`. It neither downloads an SDK nor signs, installs, starts or changes the phone. Reports mark the development-managed payload explicitly and keep `production_binary_tested=false`.

The tool calls [Microsoft DUMPBIN /IMPORTS](https://learn.microsoft.com/en-us/cpp/build/reference/imports-dumpbin), which includes static and delay-loaded imports, and retains only bounded DLL basenames, payload-relative names, hashes and closed classifications. The child uses English tool output for the parser; the parent environment is unchanged. Fixed buffers refuse stdout beyond4MiB or stderr beyond64KiB while reading. Each actual reader process has a15-second deadline and is stopped/waited if it remains. A cleanup failure cannot replace the original read/parse failure. The image loop refuses further work after10 minutes,2048 images or512MiB per image; final file hashes are rechecked before the report completes.

The updater is classified against its own copied payload, because it runs outside the installed application. A DLL present only in the parent app directory does not become an updater dependency candidate. The report distinguishes bundled candidates, API-set contract names, files found on the host in System32, external VC++ runtime dependencies, debug CRT dependencies and unresolved names. The presence of a CRT on a Visual Studio build runner is explicitly not evidence that it ships with the app or exists on a clean customer machine.

`observed_unqualified` means a static import inventory completed. It does not prove Windows loader/search-path behavior, imported function availability, runtime `LoadLibrary` requests, clean-machine installation, calling or Store certification. Even a bundled candidate needs the exact final artifact's dependency/architecture/licence review. Use Microsoft's [DLL redistribution guidance](https://learn.microsoft.com/en-us/cpp/windows/determining-which-dlls-to-redistribute) to select the supported runtime delivery route after inspecting the actual report. Do not copy a build machine's System32 files or declare redistribution complete from their presence.

Portable controls use explicit DUMPBIN-output fixtures for parsing/classification, including unsupported descriptor indentation, plus actual offhost refusal and original-primary preservation. Actual subprocess tests cover bounded stdout/stderr overflow, original nonzero exit, timeout, fresh observed child PIDs and the shared failure/cleanup handler. The package hook runs after the unchanged original preservation baseline, before certificate creation; it records an additional fixed vector observation and the separate inventory report hash. It never downloads or repairs missing dependencies. The main workflow must require the control script and upload only the fixed bounded report pattern. No actual Windows import report has been accepted yet, and workflow activation remains pending review.
