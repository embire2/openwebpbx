# 3CX reader verification

Run `php tests/threecx_backup_parser.php` with PHP DOM/XMLReader/mbstring/zip enabled. The fixtures are synthetic and include invented credentials. Tests create private temporary files and remove them. They never connect to a PBX or SMTP service.

The legacy adapter recognizes the verified v14/v16 envelope `PhoneSystem/header/version`, `PhoneSystem/Gateways/{VoipProvider,Gateway}`, and `PhoneSystem/Tenants/Tenant/{DN,OutboundRules}`. One tenant is required. Core user fields come from `DN/Extension`; trunks join `DN/ExternalLine/Gateway` to provider `Name`, with credentials on the external line. An outbound rule must have one nonempty route and no extension/department restriction. Its provider must resolve to one external line. Inbound rules migrate only exact DIDs with the same destination in both office-hours and out-of-office-hours rules. Other behavior is listed in `unsupported`.

A separate native V20 adapter now supports the observed Update 9 build `20.0.9.995`, including its supported calling objects and private media. See [V20 restore](../docs/v20-restore.md) for the wider mapping and remaining differences. The optional `tests/pbx_v20_restore_integration.php` check uses an operator-supplied private backup via `OPENWEB_PRIVATE_BACKUP`; it creates an isolated schema and removes its restored test files. The customer archive is never a public fixture.

Evidence read during implementation:

- [Public MIT converter source](https://github.com/ninjanody/Elastix5Converter/tree/master/templates) includes `backupDb.xml` version `14.0.0.0` and original extension, external line, provider and outbound rule templates. The implementation was written independently; no customer data or external XML fixtures were copied into this repository.
- A [public converter artifact](https://github.com/QuendaltonBreed/Donegal3CX) contained a native XML envelope with version `16.0.1.273`. It was inspected in memory for tag paths and attribute names only. Credential values and customer records were not logged or retained.
- [Official 3CX setup documentation](https://www.3cx.com/docs/configure-pbx-automatically/) and its [official V20 setup sample](https://downloads-global.3cx.com/downloads/misc/setupconfig_v20.xml) describe the separate `SetupConfig` export. That export is clearly labeled and is never called a native backup. External `BackupFile` references are not fetched.
- [Official V20 Update 7 announcement](https://www.3cx.com/blog/releases/admin-system-management/) describes Backup & Restore V2. It does not publish the native archive/XML schema. Initial native V20 support remained disabled until the user supplied a private Update 9 sample; its layout and restore behavior were then validated. V18, other native V20 builds, encrypted containers and unfamiliar layouts remain unsupported until their version-specific adapters and checks are added.

`supported=true` means the envelope is recognized and some core configuration is safely mappable. It does **not** mean full restore or behavior parity. Any import must show warnings and unsupported records, require acknowledgement of omitted behavior, and leave trunks and inbound routes disabled for carrier review.

The parser reads one root `*Db.xml`, `backupDb.xml`, or `setupconfig.xml` into memory; supported V20 media is separately streamed and validated by the restore layer. Current parser limits are 2 GiB upload, 8 GiB expanded archive data and 5,000 entries. Configuration XML is limited to 8 MiB, 32 levels, 250,000 reader nodes and 2,000 core records per category. Compression checks and media-specific validation also apply; web-server upload limits can be lower. Unsafe paths, duplicate names, links, special files, encryption, unknown compression, malformed XML, DTDs, entities and unsupported namespaces are rejected. `preview()` uses field allowlists and exposes only presence flags for SIP usernames, authentication identifiers, passwords and voicemail PINs. Future compatibility work is tracked in [3CX.md](../3CX.md).
