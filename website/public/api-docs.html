Create and use an API key

  1. Sign in to Tenant Admin, PBX Administration or My PBX and open API Keys.
  2. Choose a name, expiry and the minimum permissions your integration needs. Administrative keys select a tenant and optional PBX. Personal and staff keys are automatically bound to their own account and PBX.
  3. Copy the secret once and store it in your application’s secret store. Send it in Authorization: Bearer <key>; never put it in the URL.
  4. Start with GET /capabilities and a read request. Save the returned PBX UUID for administrator endpoints; personal endpoints use /me without accepting another user’s UUID.

Coverage

The endpoint reference covers tenant onboarding and email verification (v1), templates and service creation, reseller packages and resource approvals, API keys, extensions, SIP providers and DIDs, ring groups, queues and callbacks, digital receptionists, departments and schedules, routing previews, recordings and voicemail, Keoma greetings, hotel services, audio/video conferences, phone recovery and migration, global mail, updates and encrypted backup/restore. Native phones continue to use the existing device-authenticated mobile API and SIP media services; a REST key is not a replacement for a SIP login.

Permission and data rules

Every request rechecks the key, expiry, owner account, live role, tenant availability and selected PBX. Revoked or moved staff lose access. Personal/department scopes cannot be mixed with administrator scopes. A child key cannot exceed its parent’s scopes, tenant/PBX boundary or expiry; parent revocation also withdraws descendants. List responses remove phone/provider passwords and server paths. Explicit QR/credential/invitation actions return private connection material only with their required scopes.

Viewing, scanning or emailing a QR code does not rotate it. A QR reset requires its separate explicit endpoint, write scope and confirmed: true. Changing an app password preserves desk-phone SIP passwords and follows the existing app-device revocation rules.

Requests, jobs and recovery

Use HTTPS with server-to-server requests. Browser Origin calls and query-string tokens are rejected. Each key allows 120 requests per minute; excess requests return 429 and Retry-After: 60. JSON requests are limited to 128 KiB. Replies contain data and request_id; error replies contain a safe code/message and request ID. List pagination starts at page=0.

POST commands use validated form fields, not arbitrary JSON merge patches. Send the complete settings you intend to save. Read projections deliberately omit secrets and are not private configuration exports. Destructive operations require the documented confirmation. Backup/restore, mail, greeting generation and update requests may queue jobs: an accepted request is not proof of completed restoration, email delivery or installation. Verify backup state before confirmed restoration. Full recovery revokes machine API keys. API keys cannot execute arbitrary SQL or FreeSWITCH commands.

Quick examples

curl --fail-with-body -H "Authorization: Bearer $OPENWEBPBX_API_KEY" \
  https://openwebpbx.com/api/v2/capabilities

# A personal key: the account is derived from the key
curl --fail-with-body -H "Authorization: Bearer $OPENWEBPBX_API_KEY" \
  https://openwebpbx.com/api/v2/me

# PBX administrator: supply the domain_uuid from your key or service list
curl --fail-with-body -H "Authorization: Bearer $OPENWEBPBX_API_KEY" \
  "https://openwebpbx.com/api/v2/pbx/$DOMAIN_UUID/users"

Four steps

From registration to your tenant portal

01 / REGISTER

Create the account

Send company details and an administrator email.

02 / VERIFY

Confirm the email

Redeem the one-use code and save your API token.

03 / CREATE

Choose a PBX template

Create a service with a unique request key.

04 / CONNECT

Wait for the address

Poll readiness, then open the returned tenant URL.

1. Request a tenant account

Present the terms and privacy policy in your own onboarding flow before accepting registration. Choose a unique password of 12–72 UTF-8 bytes, including a letter and a number, and a short company label of 3–40 lower-case letters, numbers or hyphens.

Register · cURL
curl --request POST 'https://call.openweb.co.za/api/v1/registrations' \
  --header 'Content-Type: application/json' \
  --data '{
    "tenant_name": "Example Company",
    "slug": "example-company",
    "email": "owner@example.com",
    "password": "replace-with-a-long-unique-password-42",
    "accept_terms": true
  }'

A valid request returns 202 Accepted with status: "verification_required". This generic response protects existing accounts; it does not reveal whether an email or label already exists and does not prove inbox delivery.

2. Redeem the email code

The global outgoing-mail service sends a code valid for 30 minutes. Send it with the same password you chose at registration in a POST body. Opening an email or following a link alone never activates a tenant.

Verify · cURL
curl --request POST 'https://call.openweb.co.za/api/v1/registrations/verify' \
  --header 'Content-Type: application/json' \
  --data '{"token":"VERIFICATION_CODE_FROM_YOUR_EMAIL","password":"YOUR_ORIGINAL_REGISTRATION_PASSWORD"}'

Successful verification returns 201 Created with the tenant, a new access_token, its expiry and token metadata. Store the token securely in your integration’s secret store. Subsequent read endpoints never reveal it.

3. Choose a template and create a PBX

Read GET /templates, then use a returned template UUID. Send a new UUID in Idempotency-Key. Keep that key for retries of the same intended operation.

Create a PBX · cURL
curl --request POST 'https://call.openweb.co.za/api/v1/services' \
  --header "Authorization: Bearer $OPENWEB_TOKEN" \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: 9b484c7d-4e6f-48b2-b9fd-c55260d8b563' \
  --data '{
    "template_uuid": "TEMPLATE_UUID_FROM_THE_LIST",
    "service_name": "Main Office",
    "slug": "main-office",
    "subdomain": "example-company"
  }'

The response contains a new service and its subdomain status. Creation uses the current installed application files and the selected template’s current revision. Provider secrets are not exposed. Only shared published starter templates explicitly approved by the instance administrator are eligible, with no trunks, outbound rules or additional settings. If the list is empty, ask the instance administrator to publish an approved starter template. Configure your own provider after creating the PBX.

4. Poll the address until ready

Check tenant address · cURL
curl 'https://call.openweb.co.za/api/v1/services/SERVICE_UUID/subdomain' \
  --header "Authorization: Bearer $OPENWEB_TOKEN"

Wait for ready: true, then use the returned url and admin_url. The address guide explains pending DNS, certificates and collision handling. Set up a provider and test incoming and outgoing calls before moving live numbers.

Authentication that stays with the tenant

Already verified? Send POST /auth/token with your owner email and password. Protected operations use Authorization: Bearer TOKEN. Browser sign-in cookies and phone passwords do not authenticate this API.

Authenticated request · cURL
curl 'https://call.openweb.co.za/api/v1/me' \
  --header "Authorization: Bearer $OPENWEB_TOKEN"

Tokens start with owta_, followed by 64 hexadecimal characters. They expire after at most 90 days, with a default of 90 days. The server stores hashes, not usable token secrets. Each request checks that the owner and tenant remain active.

To change your account password, use POST /me/password with current_password and new_password. This revokes every previous owner API key, including the key making the request, and returns a replacement. Save that replacement before your next call. SIP, extension and phone-app passwords are unchanged.

Create a separate named token for each integration with POST /tokens, rotate it when needed and revoke it when no longer used. A tenant may have up to 10 active tokens. Rotation invalidates the old secret. A token-creation or rotation response is not saved for later secret recovery; if a response is lost, sign in again and review/revoke unused tokens.

A managed address for each PBX

Pass a single label such as example-company when creating the PBX, or use POST /services/{service_uuid}/subdomain for an existing owned service. Labels have 3–40 lower-case letters, numbers or hyphens and must start and end with a letter or number. Reserved names are refused. Omit subdomain during service creation to use the tenant slug.

GET /subdomains/availability?label=example-company is a local, advisory check. Its response has scope: "this_instance" and reservation_confirmed: false. It does not reserve global ownership or make a DNS request.

The central custodian confirms ownership and may assign a stable suffix for a label held elsewhere. Always use the final assigned hostname from status, rather than constructing it from your requested label. Once an address is queued or leased, it cannot be silently renamed. The initial custodian limit is 50 names per instance, including existing reserved names.

Self-installed servers and Webhotel.cloud images

Your own server. One simple setup.

Installing OpenWeb PBX on your own server? Open the setup wizard and use the code displayed by the installed server. Confirm your account email, choose a business address and keep the server running while its secure connection is prepared. Your PBX, database, calls and recordings stay on your own installation.

Set up my serverDownload wizard API

Debian 1.0.23 includes guided registration, the first-boot consumer and mandatory registration for fresh installations. See the Debian installation guide and the qualified release scope. Windows Server 1.0.23 uses the same guided registration flow on Windows Server 2025 x64 with Desktop Experience. Signed Windows 1.0.23 upgrades require installed Windows 1.0.22 or newer; see its qualification record for actual component and reused-recovery scope. Follow the Windows installation guide for local setup and registration.

Public pairing checks cover real custodian DNS, Let’s Encrypt certificates, signed authorization and verified tenant HTTPS readiness. The release report records exact installer, upgrade, restore and provider-image acceptance. Test verification mail was intercepted privately; these checks do not establish new inbox delivery, physical handset or carrier acceptance.

Two integration paths

  • Browser or Webhotel image: use the dedicated /api/v1/wizard API and its 20-operation specification. The image receives a private device credential; the owner’s password and bearer token stay out of the guest. No custom hostname or certificate is needed before pairing.
  • Installed administrator wizard: sign in to the local PBX, confirm the owner email and use the seven installation operations below. The worker proves its P256 identity on its trusted canonical hostname and verifies the authority’s pinned RSA receipt.

Remote authorization creates no hosted /services row. A browser receives a connection link only after the actual tenant HTTPS proof and custodian ownership match. Always use the final assigned tenant hostname, including a collision suffix if one is assigned. Existing desk-phone domains, credentials and working connections are preserved.

Provider checkout and cancellation

Hosting integrations check global availability with POST /wizard/subdomains/availability, then reserve the chosen name for a verified owner before taking payment or creating a server. The reservation is bound to the installed server during claim. A separate encrypted cleanup credential stays in the provider backend and never enters the guest or browser.

To remove an instance, the provider first confirms its own virtual machine is stopped, then requests exact scoped cleanup through POST /wizard/servers/revoke. Only a fresh confirmed response permits address release. Conflicting ownership or uncertain DNS cleanup keeps those resources reserved for recovery. See the wizard specification for exact fields and retry rules.

Installation authorization sequence

  1. Register/verify or sign in to your existing owner account. An invited owner confirms their current email with /onboarding/email/request and /onboarding/email/verify.
  2. Request /installations/challenge with canonical server hostname, public P256 key, local tenant/domain UUIDs and the chosen label.
  3. The installed worker publishes the returned nonce proof and signs the exact challenge message. Submit POST /installations; verify the signed receipt against the independently pinned public key before storing it.
  4. Let the existing tenant-domain worker prepare DNS and trusted HTTPS. Authorization alone does not mean the tenant address is ready.

For exact signature bytes, provider-image preparation and local helper contracts, read the downloadable Webhotel and first-boot contract. The central API never receives a private instance key or exposes DNS provider credentials.

Safe retries and clear limits

PBX creation and subdomain registration require a UUID Idempotency-Key. Retrying the same JSON request with the same key returns its saved result and Idempotent-Replayed: true. Poll the subdomain resource for its current readiness; the original saved response can still show a pending state. Reusing that key with changed details returns 409. Use a new key only for a genuinely new intended operation.

New public tenants begin with one PBX service. The instance operator controls admission and quotas; the default public-signup cap is 25 tenants. This is not an offer of unlimited hosted capacity.

OperationDefault limit
Register5 per source IP/hour; 3 per email/hour; 100 globally/day.
Verify30 per source IP/10 minutes.
Sign in20 per source IP/10 minutes; 8 per email/10 minutes.
Change account password5 attempts per owner/10 minutes.
Authenticated API120 requests per tenant per minute, shared by its tokens.

On 429, honor Retry-After. On a timeout or temporary 503, use bounded exponential backoff and keep the original idempotency key for a write. Correct validation, authentication and conflict errors before retrying. Do not retry forever or repeatedly create new tokens after losing a response.

What your integration can control

Public self-service tenants use the modern Desktop and Tenant Services portals. Direct legacy administration pages remain unavailable to these accounts; existing invited tenants keep their current permissions.

Every protected operation is scoped to its verified tenant owner. Clients cannot choose arbitrary tenant identities, grant platform roles, supply DNS credentials, take another company’s name, read trunk passwords or execute operating-system commands. An unavailable or foreign-owned service is not disclosed.

Use a server-side integration and normal HTTPS certificate validation. Browser-cookie authentication and cross-origin browser requests are not supported. JSON request bodies are limited to 32 KiB and unknown fields are refused. Keep tokens in a secret store and send them only in the Authorization header, never in URLs.

There is no destructive tenant-installation or recording-deletion operation in this API. For account or personal-data removal, use the deletion procedure. Registering a tenant does not activate paid provider trunks or assign carrier numbers.

Verification uses the installation’s global outgoing-mail service. A queued message or SMTP acceptance does not prove inbox delivery. DNS and certificate readiness can take time; preserve a working connection while an address is pending.
